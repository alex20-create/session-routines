# Handover and retro

Read this when the account's usage is high, when the director's own context is filling up, or when the project ends.

## Watching usage

At each report, read `get_usage`.

- Near the account's 5-hour limit (above about 80%), say so in the report and ask every working session to commit at the end of its current piece. The limit stops every session at once.
- Every piece ends in a commit anyway, so a stop loses nothing. If the briefs' shared rules do not say "commit at the end of each piece", propose adding it to the user; the template's rules carry it.
- Near a weekly limit, tell the user once; the model policy is theirs to change.

## A new director

After about eight pieces, or when the director's own context passes about two thirds (`get_usage` with its own session), hand over:

1. Bring `STATUS.md` up to date and commit it.
2. Check `DIRECTING.md` still says how things are (resources, starting rules, clock).
3. Give the user the opening line from `DIRECTING.md`, ready to paste into a new session. Nothing else is handed over: the files are the handover.

A new director's first step is to check `STATUS.md` against the real files and git before trusting it, then tell the user in five lines where things stand.

The same goes for a standing role: its holder updates «State» in its role file and gives the user its opening line.

## The retro

When the project, or a big stage of it, ends:

1. With the user, briefly: the «Done» times against the ranges given; what was lost, late or cut, and why; traps paid for.
2. Sort each lesson:
   - about directing in general: propose it as a change to this skill;
   - about this machine or this user's setup: their local map;
   - about this project: the project's own instructions or memory.
3. Ask before writing any of them.
4. Then offer the session close-out routine if one is installed.
